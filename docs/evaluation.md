# 評估集：從「有沒有差」到「哪個比較好」

`mode_overlap` 只能告訴你五個模式的結果**不一樣**。它永遠答不出**哪一個比較對**——因為沒有標準答案。這是這個實驗最根本的天花板。

有了可用的內部 LLM，就能讓它讀一篇 concept，產出「**這篇文件是哪個問題的答案**」。拿到的不只是查詢，是 `(查詢 → 已知相關文件)` 的配對——一組標籤。有標籤就能算 recall@k 與 MRR。

```bash
uv run yedai gen-evalset ./bundles -n 30 -c config.local.yaml   # → evalset.local.jsonl
uv run yedai evaluate -f evalset.local.jsonl -o eval.json -c config.local.yaml
uv run yedai report -e eval.json -o report.json -c config.local.yaml
```

## 兩個必須一直帶著的偏誤

這一節不是免責聲明，是**判讀方式**。

### 1. 標籤只涵蓋一篇相關文件

來源 concept 只是「一篇」相關文件，不是「唯一相關的」。同一個查詢很可能有別的 concept 答得一樣好甚至更好，而那些會被算成未命中。

**所以 recall@k 是下界、MRR 偏低，絕對值不可外推。** 看到 `recall@10 = 0.42` 不代表「四成的查詢找得到答案」。

但這不影響它的用途：**五個模式面對同一組標籤與同一組偏誤**。要下的結論是

> B 比 A 高了多少

而不是

> B 的絕對 recall 是多少

偏誤在模式之間是共同的，所以相對差距成立。

### 2. LLM 照抄文件裡的罕見詞

LLM 看著文件寫查詢，很容易把文件裡的專有詞原封不動搬進查詢——那會讓 BM25 系（A/B/C）虛胖，稠密腿（D）被低估。

提示詞用「假設你沒讀過這份文件」壓一部分，但壓不掉全部。

**所以指標依查詢種類拆解**：

| 種類 | 內容 | 怎麼讀 |
|---|---|---|
| `identifier` | 帶機台／批號／站點 | A/B/C 佔優是**預期內**的，沒有資訊量 |
| `symptom` | 完全不含識別碼與代號 | 這一欄才是有訊息量的。D 若在這裡輸給 C，稠密腿就真的不值得 |

只看總分會把兩件事混成一個數字。**先看 `symptom` 那一欄。**

## 未命中計入分母

找不到的查詢仍然計入所有模式的分母，MRR 貢獻為 0。把它們排除會讓表現差的模式看起來更好——而那正好是這份量測要分辨的東西。

## 語料外流閘門

`gen-evalset` 會把 concept 全文送到 chat 端點，與 `embed` 同樣的風險，沿用同一道閘。

**`llm` 與 `embedding` 的信任宣告各自獨立。** 兩者現在指向同一個 LiteLLM，但把信任從一個端點自動延伸到另一個，正是這道閘門要防的事。

```yaml
llm:
  base_url: http://litellm.internal/v1
  model: kimi-k2.7            # 要與你的 LiteLLM 登記的 model 名稱一致
  api_key_env: LITELLM_API_KEY
  temperature: 0.0            # 重跑時盡量得到同一組標籤，否則兩次評估無法比較
  trusted_endpoint: true
```

## 失敗的 concept 會被跳過，但數量看得見

一批可能是幾百次請求。為了一次格式異常全部重來，代價是這個工具不會被跑第二次。所以單一 concept 解析失敗就跳過。

但失敗數會印出來也會寫進檔頭——**靜靜跳過會讓評估集悄悄偏向「LLM 剛好答得出來的那些文件」**。失敗數偏高時，這組標籤的代表性就要打折。

## 快取

LLM 回應落地快取，鍵含模型名稱。任何一次調整（改提示、改取樣數）都不必整批重付——不然「調整」會變成不敢做的事。

換模型後快取自動失效：混合兩批不同模型產的標籤，會得到一個對應不到任何可解釋產生過程的標籤集。

## 報告只帶數字

`report -e eval.json` 會把指標併進去識別化報告。**查詢原文不會進去**——它是語料衍生物、帶真實識別碼，而報告是唯一設計為可外流的產出。這條界線有測試把關。
