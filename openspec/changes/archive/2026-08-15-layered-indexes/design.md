## Context

目前 `build_index(root)` 把根目錄底下所有 bundle 灌進單一 `Index`，其中持有 `naive` / `protected` 兩套 `TermSpace` 與一套 `EntitySpace`。那兩套詞彙空間是**模式 A/B 的變因**，不是不同語料——整份索引服務的是同一個語料集合，`df`、`avg_field_len`、實體 idf 全部是全域的。`DocMeta.bundle_id` 有記錄來源，但檢索路徑上沒有任何地方讀它。

即將接入的語料是四類性質不同的查案知識：

| 類別 | 來源 | 規模 | 格式 | 檢索性質 |
|---|---|---|---|---|
| 查案心法 | 人寫 | 大量 | 自由文字，無固定格式 | 真正的文字檢索；查詢是 agent 下的子查詢 |
| closed cases | 系統匯出 + 工程師結案 | 持續累積 | 固定格式（多頁、多模態） | 同格式文件比對，文字只是其中一維 |
| defect library | 人寫 | 每個 defect 一條 | 半結構化 | 查詢多半是視覺的；同時是實體字典來源 |
| defect→module taxonomy | agent 產 | 每個 defect 一條，部分填充 | 判斷方法的文字描述 | 以 defect 為鍵取回，不是檢索 |

現有的 BM25F + 實體 + 稠密 + RRF 那一整套機制，在**心法層**完全對症；在其他三層它不足或不適用。這個認識是本次設計的前提。

## Goals / Non-Goals

**Goals:**

- 每個索引持有完全獨立的詞彙與實體統計，使一層的成長不影響另一層的排名。
- 每層可宣告自己的檢索設定與 query 前處理，使同一個查詢字串以不同形式進入不同層。
- 檢索結果保留層結構，缺席可辨識。
- taxonomy 脫離檢索路徑，成為以 defect 為鍵的查表資源。
- 把「新增 closed cases 不改變心法層結果」變成可執行的回歸測試。
- 保持機密邊界：機制與 schema 進 repo，內容走 `.local`。

**Non-Goals:**

- closed cases 層的結構化比對（module / 站點 / defect type 分佈 / wafer history 機台交集）——後續 change。
- 以歷史結案做 root-cause 回放評估——後續 change。
- defect report 逐頁攝入與頁型分類——後續 change。
- 圖像檢索（defect map / SEM）。本次僅維持既有的「圖說進索引、圖本身不進」。
- 增量索引。分層本身已把重建成本關進單層，先花這筆時間紅利。
- 時間衰減排序。那是排序信號不是索引結構，現在做會混淆兩件事。

## Decisions

### D1：真正分開索引，不是單一索引加過濾

**選擇**：每層一個獨立的 `Index` 實例與獨立的檔案，各自持有 `TermSpace` / `EntitySpace`。

**替代方案**：保留單一 `Index`，查詢時以 `bundle_id` / `type` 收斂 `candidates`。改動小很多——`Searcher._hybrid` 已經支援 `candidates: set[int]`。

**否決理由**：`candidates` 只影響誰參與排序，`df` 與 `avg_field_len` 仍取自全語料。idf 漂移的問題原封不動——心法的詞在全語料看來永遠罕見，而且每進一批 closed cases 就變一次。這正是要解決的問題，過濾方案沒有觸及它。

### D2：預設分層回傳，跨層融合是顯式選項

**選擇**：檢索回傳 `{layer: [hits...]}`，各層各自 top-n、各自帶分數，**不跨層排序**。跨層 RRF 融合保留為顯式參數，供對照實驗。

**替代方案**：跨層 RRF 平權融合為預設；或依語料規模加權融合。

**否決理由**：

RRF 融合的前提是兩份排名在回答同一個問題。跨模式（C 與 D）滿足——同一份語料、同一個問題、失效模式互補。跨層不滿足：「這篇心法比那筆 closed case 更相關」不是有意義的命題，它們回答的不是同一件事。要讓它們比大小就得發明一個共同尺度，而那個尺度不存在。

規模加權更糟——`rrf()` 的既有註解已經說明過為什麼不引入猜出來的權重，這裡會是同一個病換個地方發作。

分層另有三個具體好處：**缺席變成訊號**（心法層為空 = 這類問題沒有既定查法，跟「排在第 11 名」可區分）；**結構是給 agent 用的**（壓平之後它得再猜回來）；**與 D3 相容**（各層用不同 query、不同模式，把結果混成一個分數本來就可疑）。

保留融合選項的理由是：這個決定應該被量測，不是被宣稱。

### D3：query 前處理綁在層上

**選擇**：每層宣告自己的 query 前處理，最低限度是「是否保留識別碼」。

**理由**：同一個查詢在不同層意義不同。含機台識別碼的查詢送進 closed cases，識別碼是主訊號；送進心法或 defect library，它是雜訊——會讓檢索去比對一個跟問題無關的字串。差異發生在 query 進入檢索**之前**，這是為什麼 D1 不能退化成過濾器方案的第二個理由。

### D4：一個索引一個檔，不是一個檔多個索引

**選擇**：每個索引獨立序列化到自己的路徑。

**理由**：重建節奏依層而異。心法與 defect library 是策展的（事件驅動：有人改了才重建），closed cases 是流水的（排程驅動）。單一檔案會讓「只重建 closed cases」變成讀寫整份，且兩個重建流程會互相踩到。

### D5：signature 納入層識別，重建依賴顯式化

**選擇**：`index_signature` 納入所屬層；defect library → 其他層的重建依賴以顯式的順序表達，不依賴呼叫者記得。

**理由**：defect library 同時是 `EntityDictionary` 的來源，它變更會使其他層的實體抽取結果改變，`check_signature` 會擋下來。這是**正確**行為，但如果沒有顯式的重建順序，實際發生的會是「加了幾個缺陷名，隔天整個系統回報索引不相容」，而錯誤訊息只會說「請重建索引」，不會說該先重建哪一個。

### D6：taxonomy 走查表，而且它是 defect library 的衍生欄位

**選擇**：taxonomy 不進任何索引。以 defect 為鍵載入，查無條目時回傳明確的「無此條目」，不做近似比對。

**理由**：它是「每個 defect 一條」的判斷方法，存取模式是以鍵取回。放進倒排索引，呼叫端拿到的會是「最像的幾列」——而且會很自信。近似比對在這裡是有害的：拿錯 defect 的判斷方法去看圖，比沒有方法更糟。

更精確地說，它不是第四類對等語料，而是掛在 defect library 上的**部分填充衍生欄位**。這帶來一個第一級指標：**taxonomy 覆蓋率**（有條目的 defect 佔比，可依 defect 類別拆解）。這與既有的 `coverage_by_type` / `shape_complete_types` 是同一種東西——分母可測、缺口看得見、跟著資料一起存。

### D7：未指定索引時全查

**選擇**：呼叫端未指定索引時，對所有已載入的索引檢索並分層回傳；指定時只查該層。

**理由**：agent 的失敗模式是「不知道自己不知道」。預設全查讓它至少看見別層有東西；指定單查是它已經確定要什麼時的加速路徑，不是預設。

（後續 change 會讓 module 判斷結果成為收斂訊號——那是比 agent 自己猜更好的路由。本次先把介面留出來。）

### D8：向量 collection 依索引命名

**選擇**：每個索引宣告自己的 qdrant collection。

**理由**：跟 D1 同樣的隔離理由，另加一個：不同層的稠密腿價值不同。心法層預期稠密腿是主力（敘述性、查詢用詞與文件用詞對不上），closed cases 層預期不是。分開 collection 才能分開決定要不要付這筆 embedding 成本。

## Risks / Trade-offs

**[小層的 idf 估計變噪]** → 分開統計解決了漂移，但也縮小了每層的統計基數。文件數很少的層，`df` 樣本不足會讓 idf 估計不穩。這是 D1 的真實代價，不是可以繞過的。緩解：報告依層列出文件數與詞彙量，讓「這一層小到統計沒有意義」看得見；若某層確實過小，該考慮的是它要不要獨立成層，而不是回頭共用統計。

**[層邊界劃錯很難改回來]** → 一旦資料按層落地、按層重建、按層評估，改變邊界等於全部重來。緩解：本次只切出四類中確定不同質的三個索引 + 一個查表；不預先細分（例如 closed cases 依時間分片）——那些等有量測數據再說。

**[呼叫端變複雜]** → 分層回傳把「一個列表」變成「一個結構」。人類介面（CLI 輸出、Swagger）要多做呈現工作。緩解：CLI 分層印出並標示空層；HTTP 回應納入 OpenAPI schema（既有要求，不是新增負擔）。

**[重建從一次變多次]** → 全量重建所有層的總成本略高於原本的單次重建（每層各自 finalise、各自序列化）。但單層重建的成本大幅下降，而那才是日常操作。判斷是淨賺。

**[BREAKING 設定變更]** → `index_path` 移除會讓既有 `config.local.yaml` 直接失效。緩解：載入舊 key 時明確報錯並指出新形狀，不靜默忽略——靜默忽略會讓使用者以為索引建好了，實際上建到預設路徑去。

**[分層是否真的優於融合，目前是設計判斷不是量測結果]** → D2 的論證是原理性的（兩份排名是否回答同一問題），不是實證的。緩解：保留融合選項，並在後續的 root-cause 回放評估中把兩者當成一組變因比較。如果數據推翻這個判斷，改預設值的成本很低——結構已經在了。

## Migration Plan

1. 提升 `INDEX_FORMAT_VERSION`。既有 `.index/*.pkl` 全部失效，`Index.load` 會明確報錯要求重建（既有機制）。
2. 設定遷移：偵測到舊的 `index_path` key 時報錯並印出新的 `indexes` 形狀範例。不做自動轉換——舊設定沒有層的概念，自動猜測會猜錯。
3. 更新 `config.example.yaml` 與 taxonomy 資源的 example 檔；確認 `.gitignore` 涵蓋對應的 `.local` 檔。
4. 以 `.synthetic/` 作為過渡期的單層語料驗證整條路徑，再接入真實分層語料。

**回滾**：本次不改變任何持久化的使用者資料——索引與向量都是可重建的衍生物。回滾即還原程式碼與設定後重建索引。

## Open Questions

- **每層的預設 n 是多少？** 分層回傳沒有全域 top-k 可切分，每層的深度是獨立參數。合理起點是各層相同，但心法層（量大、品質參差）可能需要更深才撈得到有錯定的內容。等有評估數據再定。
- **心法層要不要再細分？** 「大量且無固定格式」可能意味著它內部也不同質。目前當成一層處理；若品質信號顯示它有明顯的子群，再談。
- **closed cases 的檢索單位是整份 report 還是單頁。** 現行索引以 concept（頁）為單位，`bundle.summary` 不進索引，因此沒有 report 級的可檢索單位。這是後續 change 的核心問題，但本次的索引結構不能把它堵死——分層的 schema 需要能表達「檢索單位是 bundle」這件事。
- **心法的品質信號從哪來。** 已識別三種（與 defect library 的一致性、結構性特徵、使用信號），其中使用信號目前收不到——`/feedback` 沒有可用介面。不阻擋本次，但它決定心法層最終能做到多好。
