# 設計

## 一、`#` 為什麼不能沿用既有的正規化規則

`normalise_identifier` 目前移除 `- _ 空白` 後轉大寫，讓 `TEL-05` / `TEL05` / `tel 05` 收斂到同一詞元。**`#` 不能比照辦理。**

移除 `#` 會讓 `aepol1#pm1` 正規化成 `AEPOL1PM1`。那個字串本身沒有錯，但它與「機台 `aepol1` 的腔體 `pm1`」之間的關係就此消失，之後任何想利用父子關係的機制都得重新反推分界點——而分界點是不可靠的（`aepol1` 與 `pm1` 都是變長的）。

保留 `#` 的代價是零：它不會出現在人類的多種寫法變體裡（沒有人把 `aepol1#pm1` 寫成 `aepol1 # pm1`），所以不需要為它做寫法收斂。

## 二、層級展開為什麼在斷詞層做，而不是查詢展開

有兩個位置可以做「查機台命中腔體」：

1. **索引期**：腔體識別碼同時寫入子層與父層詞元
2. **查詢期**：查詢中的機台識別碼展開成「機台 OR 所有已知腔體」

選 1。理由：

- 查詢期展開需要知道「這台機有哪些腔體」，那是字典查詢；但**未進字典的腔體就展不出來**，而字典覆蓋率正是本實驗要量測的未知數。用未知數當作另一個機制的前提，會讓兩者的效果無法區分。
- 索引期展開只依賴字串結構，不依賴字典。它在字典為空時同樣正確。
- BM25F 的 idf 會自動處理副作用：父層詞元因展開而變高頻，idf 隨之下降，鑑別力的損失是被計分公式吸收的，不需要額外調參。

代價是索引體積略增（每個腔體識別碼多一個詞元）與父層詞元的鑑別力下降。後者是這個決策的真實成本，記在此處以便日後回推。

## 三、`find_identifiers` 必須同步展開

`protected()` 供詞彙腿使用，`find_identifiers()` 供實體抽取使用。兩者共用同一組正則，但**輸出路徑不同**。

只改 `protected()` 會造成一個難以察覺的分歧：詞彙腿認得父層、實體腿不認得。同一個查詢在模式 B 與模式 C 會表現出不一致的「找不找得到腔體文件」，而這種不一致會被誤讀成「實體腿沒有用」。

`find_identifiers` 回傳含 `(start, end)` 位置。父層詞元沒有獨立的位置區間——它是子層區間的一部分。實作上讓父層沿用子層的區間；位置資訊目前僅供 `literal_scan` 的去重與除錯，重疊不影響正確性。

## 四、CSV schema 為什麼不做成通用讀取器

兩種來源的欄位語義完全不同：

```
id_only            單欄，值本身即 canonical，有無 # 決定實體類型
module_code_name   三欄，Module 是中繼資料，code 是 canonical，name 是別名
```

寫成通用讀取器就得引入「欄位對應設定」，而欄位對應設定的錯誤是**靜默的**——把 `Module` 對成 canonical 不會報錯，只會產出一份看起來正常、實則整份錯誤的字典。依類型各自解析則能在載入時就驗證欄位數與標頭，錯了立刻失敗。

新增類型的成本是一個解析函式，而類型的數量以年為單位變動，不值得為它付通用化的代價。

## 五、機台與腔體同表的類型判定

單欄 CSV 無法宣告「這列是機台還是腔體」，但值本身可以：含 `#` 即為腔體。

這個規則刻意寫在載入器而非設定檔——它不是使用者偏好，而是資料本身的性質。放進設定檔會給人「可以改」的錯覺，而改了它只會產生一份類型全錯的字典。

## 六、別名的語言混合：為什麼採「全都註冊」

`defect name` 可能是純中文、純英文，或同格中英並存。三種情況的正確處理方式不同，而我們不需要事先知道是哪一種：

- 整格註冊 → 覆蓋純中文、純英文，以及使用者完整貼上整格的情況
- 中文段、拉丁段各自註冊 → 覆蓋同格混合時使用者只打其中一種語言的情況

代價是字典條目數略增，且同格混合時會有一個別名對應到與整格相同的正規名稱——那正是我們要的行為（`code` 與 `name` 一對一綁定，反查無歧義）。

分段切在 CJK 與非 CJK 的交界，**不沿用 `Tokenizer._plain` 的詞元切法**。後者會把 `Pattern Collapse` 拆成 `Pattern` 與 `Collapse` 兩個別名，於是任何提到 "pattern" 的文件都會被判定含有該缺陷。別名要的是完整名稱，不是詞元——這兩者的需求剛好相反，共用切法會壞掉。

區塊邊緣的標點會被去除，讓 `微粒 (particle)` 得到 `微粒` 與 `particle` 而非 `(particle)`。

## 七、per-type 統計的洩漏面

覆蓋率拆解後，報告會多出以類型為鍵的結構：

```json
"by_type": { "tool_id": {"dict": 812, "regex": 44}, "defect_code": {"dict": 251, "regex": 0} }
```

鍵是**類型名稱**，屬 schema；值是計數，屬統計。兩者都不是語料內容。正規名稱（`AEPOL1`、`PARTICLE`）MUST NOT 出現在報告中——那才是會讓報告無法帶出公司的東西。

`unknown` 類型（regex 命中但字典未涵蓋）仍以 `unknown` 為鍵，不展開其正規名稱。

## 八、索引格式版本

斷詞行為改變 → 舊索引的詞彙空間與新程式不相容。`INDEX_FORMAT_VERSION` 3 → 4。

不採「自動重建」：語料規模預期達 220 萬 concept，重建是分鐘到小時級的操作，必須由人明確發動。載入舊格式時拒絕並提示重建指令。
