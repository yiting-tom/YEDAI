## Context

YED 的 OKF 語料目前約 30 個 bundle（每 bundle 15~30 個 concept，每個約 300 行），預計成長到 10 萬個 bundle。現階段 agent 用 grep/glob 就有很好的效果，但那是小規模才成立的條件。

語料有三個決定性特徵：

1. **文字主體是識別碼**——機台 id、製程 id、flow 名稱等專有字詞，而非自然語散文
2. **類型重複度高**——查案／訓練／生產會議各自套用固定模板，內容不重複但結構重複
3. **全由同一個模型產生**——文風與用詞高度一致，鑑別力集中在少數識別碼上

前兩點合起來意味著：一般斷詞會把 `TEL-05` 切成 `tel` + `05`，與 `TEL-06` 只差一個低鑑別力 token。這個假設**尚未經過實測**，本變更的存在就是為了驗證它。

額外約束：真實語料為公司最高機密，不可外流、不可進版控、開發者無法取得樣本。

## Goals / Non-Goals

**Goals:**

- 建立純關鍵字檢索的**水位線**，讓後續所有架構投資都有對照基準
- 用消融實驗回答一個具體問題：識別碼需不需要特別處理？需要的話停在斷詞層就好，還是必須維護實體字典？
- 產出**可外流的去識別化統計報告**，使數據能跨組織用於後續設計討論
- 零外部服務相依，單機可跑，讓實驗門檻降到最低

**Non-Goals:**

- 不做向量檢索、embedding、reranker——本變更刻意只做關鍵字，作為對照組
- 不做 issue family、實體稀疏向量、多層導航——待本變更的數據出來再決定
- 不追求 10 萬 bundle 的規模工程；本變更以 30~100 bundle 為設計點
- 不做權限控管與資料分級

## Decisions

### D1. 三組消融而非兩組

原始構想是「純 BM25 vs BM25+實體」兩組。改為三組：

| 模式 | 內容 | 隔離出的變因 |
|---|---|---|
| A | 天真 BM25F，識別碼被切碎 | 水位線 |
| B | BM25F + 識別碼保護斷詞 | **斷詞層**的貢獻 |
| C | B + 實體字典精確匹配加權 | **字典**的額外貢獻 |

理由：兩組實驗只能回答「合起來有沒有效」，三組能回答「哪一個干預有效」。若 A→B 已補完大部分差距，字典就不必維護——那是一筆長期的人力成本，值得用半天的額外實作換取判斷依據。

替代方案：只做 A/C 兩組，之後有需要再補 B。否決，因為屆時語料已變大，實驗不可比。

### D2. BM25F 欄位加權，而非平坦 BM25

concept 的 `title` / `description` / `tags` 與 300 行 body 的鑑別力差異極大，平坦 BM25 會讓 body 的模板文字淹沒標題。採 BM25F：各欄位獨立做長度正規化後加權合併詞頻，再做單次 BM25 計分。

預設權重 `title=3.0, description=2.0, tags=2.0, headings=1.5, figures=1.5, body=1.0`，全部可由 config 覆寫——這些數字是猜的，實驗就是要用來修正它們。

### D3. 中文用 unigram + bigram，不用 jieba

領域專有詞（製程站點、缺陷術語）不在任何通用詞典裡，jieba 會切錯且錯法不可預測。字元 bigram 對未知詞穩健、是中文 IR 的標準做法，且零外部詞典相依。代價是索引詞彙量較大，在本變更的規模下無影響。

### D4. 記憶體索引 + pickle 快取，不引入外部服務

30 bundle ≈ 660 concept ≈ 20 萬行文字，完全放得進記憶體。引入 Qdrant/Postgres 只會提高實驗門檻而不改變結論。索引建好後 pickle 到磁碟，CLI 與 API 共用同一份快取。

### D5. 融合用正規化線性加權，不用 RRF

模式 C 需要看見「詞彙腿」與「實體腿」各自貢獻了多少分數。RRF 只吃排名、會抹掉分數資訊，無法回答這個問題。改用各自正規化到 [0,1] 後線性加權，並在結果中**同時回傳兩條腿的原始分數**。

### D6. 實體字典保留 regex fallback，並統計覆蓋率缺口

符合識別碼樣式但字典未命中者，標記為 `type=unknown, source=regex`。報告中統計 dict 命中 vs regex fallback 的比例——這個數字直接告訴使用者字典的覆蓋率缺口有多大，是決定要不要繼續投資字典維護的依據。

### D7. 雙軌遙測，去識別化報告為一等公民

- **完整日誌**：JSONL，含查詢原文、結果 id、分數。寫入 gitignored 目錄，永不外流
- **去識別化報告**：只含數值與分佈，零內容。包含查詢長度分佈、實體命中率、零結果率、各模式分數分佈、**模式間 top-k 重疊度**、點選排名分佈、語料統計

模式間 top-k 重疊度（Jaccard 與 Kendall tau）是最關鍵的單一指標：若 A 與 C 的 top-10 有 95% 相同，則所有額外機制都沒有實際作用，實驗直接得到結論。

去識別化報告的正確性由測試守住：測試會斷言報告的序列化結果中不含任何查詢原文或 concept 標題。

### D8. 合成 bundle 產生器

開發者無法取得真實資料，因此需要格式相符的合成語料才能端到端驗證。產生器使用固定 seed，產出假機台號、假缺陷碼、假 flow，並套用與真實語料相同的模板結構。

**合成資料只用於驗證程式正確性，不得用於調參或推論效果**——這一點寫進 README 與產生器的輸出說明。

## Risks / Trade-offs

- **合成資料的分佈不代表真實語料** → 明確限定用途為程式正確性驗證；所有效果數字必須來自使用者在自己環境跑出的真實資料
- **識別碼正則過寬，誤圈一般英文詞（如 `bm25`）** → 報告統計被圈出的識別碼數量與分佈；樣式清單可由 config 完全覆寫；誤圈對模式 B 的影響會直接顯示在 A/B 差異中
- **點選回饋有位置偏差**（使用者傾向點第一筆） → 報告同時記錄點選的排名分佈，供後續做 propensity 校正；三模式並排時隨機化左右順序以降低偏差
- **BM25F 權重是猜的** → 全部可由 config 覆寫，並在報告中記錄當次使用的權重，確保實驗可重現
- **中文 bigram 使索引膨脹** → 本規模無影響；10 萬 bundle 時需重新評估（屆時架構本來就會換）
- **單檔解析失敗被靜默吞掉** → 解析器回報 skipped 清單與原因，CLI 與 `/stats` 都會顯示；不合格檔案數量本身就是語料品質的訊號

## Migration Plan

無既有系統，全新專案。真實資料由使用者在自己環境提供路徑，不進版控（`.gitignore` 排除 `data/`、`.index/`、`logs/`）。
